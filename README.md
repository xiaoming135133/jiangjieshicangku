## 一、项目概述

### 1.1 问题的起点：记下来了，但用不上

一个学期的课，一名理工科学生平均会拍下两三百张板书和课件。这些照片的归宿几乎完全一样：先进相册里一个叫「课堂」的文件夹，然后在期末前被从头翻到尾，最后被放弃。

问题不在采集。拍照太容易了，容易到我们误以为「记下来」就等于「学会了」。真正的损失发生在三个地方。

| 损失 | 具体表现 | 本质 |
| --- | --- | --- |
| 找不到 | 只记得「老师讲过这个题型」，却想不起在哪一页。相册按时间排序，不按知识排序 | 检索维度与使用维度不一致 |
| 连不上 | 高数上册的极限与下册的级数本是同一条线，却躺在两个学期的两个相册里 | 知识结构被时间切碎 |
| 用不上 | 期末想按模块复习，得先把三百张照片重看一遍，再手工誊抄成专题 | 组织成本没有被任何工具降低 |

一句话概括：**采集的成本降到了零，组织的成本还停在手工时代。​**我们做的不是又一个扫描工具，而是把「组织」这一段的成本也降下来。

### 1.2 现有方案走到了哪一步

这一节必须诚实，因为这条链路上几乎每一段都已经有成熟产品。先把已有的事实摆清楚，再说我们的位置。

| 环节 | 代表实现 | 已经做到的 | 仍然缺的 |
| --- | --- | --- | --- |
| 拍清楚 | 夸克扫描王、扫描全能王 | 边缘校正、去阴影、去倾斜、多页合并 | 已经完全解决 |
| 认出来 | 夸克、Mathpix、LocalMathOCR | 印刷体、手写体、公式转 LaTeX | 基本解决，准确率够日常用 |
| 按模块归类 | 夸克「板书转复习资料」 | 扫描后按函数、几何、概率等模块保存 | 归类粒度粗；检索仍靠文件名 |
| 错题定位 | 小猿 AI 等错题类应用 | 错题归类、薄弱知识点提示 | 局限于题库内，覆盖不到板书与手写推导 |
| 连成网 | Obsidian 及其 AI 插件 | 文本笔记自动生成双链与关系图 | 没有拍照入口，输入仍靠手打 |
| 公式检索 | Mathpix 等 | 输出可复制的 LaTeX | 不可按符号检索，改一处就散了 |

所以要说清楚：**「拍照 → 识别 → 归类 → 复习」这条链路，已经有人做完了，而且做得不错。​**如果我们的作品被描述成「拍照自动整理笔记」，那它就是一个跟跑项目。

#### 缝隙在两句用户原话里

第一句，来自某款成熟产品的案例描述：「她可以搜索**文件名​**查找相关题目」。搜索文件名——这四个字暴露了问题的核心。文件是**容器**，知识是**关系**。分好类的文件仍然是文件，它不会告诉你「这个公式和那道错题说的是同一件事」。

第二句，是这类工具共同的时间假设：它们都把整理当成**一次性动作**。但真实的学习是十六周持续往里加，每一次新内容都在问同一个问题——**它该长在哪？​**一次性工具回答不了这个问题，因为它们没有「现在长什么样」的概念。

我们不抢「拍得清楚、认得准确」，那一段已经商品化了。我们抢**认完之后的那一步**：把一次性的整理，变成可维护的增量结构。

### 1.3 目标用户与场景

| 维度 | 描述 |
| --- | --- |
| 用户画像 | 理工科本科生（大一至大三），每学期 3–5 门含大量推导与公式的专业课 |
| 使用节律 | 前 8 周积累素材 → 第 9–12 周开始找不到东西 → 第 13–16 周放弃整理，直接翻原始照片 |
| 关键场景 | 课堂拍板书；课后补推导；期中按模块梳理；期末只看错题与典型题 |
| 介入时机 | 第 9 周——用户第一次意识到「我找不到」的时刻，也是流失与留存的分水岭 |

选择理工科而不是全学科，是有意的收敛：公式与推导带来了可结构化的抓手（符号、条件、结论），也让我们的技术方案有明确的评价指标——公式识别对错、知识点归属对错，都能客观打分。

### 1.4 产品定位

**笔记不是存下来的，是长出来的。**

| 层次 | 含义 | 对应设计 |
| --- | --- | --- |
| 拍一张，它自己找到位置 | AI 主动提议这条内容该挂在哪，并给出理由 | 增量结构对齐（2.3.1） |
| 你觉得不对，拖一下就行 | 任何自动结果都可一键改，改完作为反馈回传 | 修正即反馈（2.3.4） |
| 十六周后它还是一张网 | 结构能持续维护，不会越用越乱 | 未归类箱与批量确认（2.3.1） |

### 1.5 核心创新点

#### 创新点一：增量结构对齐

这是本项目的核心。现有工具把「归类」当成分类问题：先有一组类别，再把内容分进去。但学习场景里**类别集合本身在演化**——第一周只有一章，第十六周有八章几十个知识点，而且章节体系是长出来的，不是预先定义的。把它当分类问题做，必然越用越乱。

我们把它当成结构维护问题。给定已有知识树 T 与新内容 x，系统输出四种关系之一：**挂载**（属于某个已有知识点）、**扩展**（作为已有节点的子节点）、**新建**（新开一支）、**待定**（说不清，先不猜）。每种结果都附带一句理由和一个置信度。

其中最反直觉、也最关键的设计是「**待定**」。多数系统强迫立刻分类，一旦分错就污染了整棵树，而用户往往不知道怎么改回来。我们允许系统说「我现在不知道」，把这类内容放进未归类箱；等攒到三到五条，再一次性问用户：「这批内容看着像新的一章，要开吗？」把 N 次打扰压缩成 1 次。

#### 创新点二：版面分区与可编辑的公式

识别准确不是我们的卖点，**能改、能搜、能重排​**才是。一张板书进来，先做版面分区：文字区、公式区、图形区、表格区，并恢复阅读顺序；公式区转成 LaTeX，同时生成 MathML 索引，使「搜一个符号」能够命中。

一个容易被忽略但很要命的细节：**永远保留原图**。任何时候用户都能点开看到原始那一页，对照确认符号与下标。识别必然有错，产品的诚实度体现在「它承认自己可能错，并且让你一眼看到原文」——这同时也是评分标准里「透明可控」的直接回应。

#### 创新点三：题目结构化与错题反查

把一道题拆成五个槽位：题干、已知条件、求解目标、图形、解法。拆开之后才有三件事可做：按知识点重组错题本；从错题反查薄弱知识点；以及最实用的一件——**当你又错在同一处时，系统能把你三个月前写下的那段推导调出来**，而不是重新讲一遍。

这里有一条必须守住的红线：**不生成答案**。赛题明确要求 AI 是助教而不是代做，「拍题秒出答案」与题意正好相反。我们给的是「这题考的是哪个知识点、你上次卡在哪一步、建议先看哪一页」。

#### 创新点四：修正即反馈

每一次用户拖动节点、改分类、拆分或合并，系统都记录一组三元组：内容特征、原建议、用户选择。这些样本按课程聚合，每周用于调整该课程的对齐阈值与提示词。

这就是「越用越准」的真实机制，而不是一句宣传语。它同时带来一个很好的可量化指标：**用户修正率**——随着使用时间推移，用户需要手动改的比例应当持续下降。这个数字无法伪造，也最能说明系统是否真的在学习。

### 1.6 与现有产品的差异

| 维度 | 扫描类工具（如夸克） | 笔记类工具（如 Obsidian） | 脉络 |
| --- | --- | --- | --- |
| 输入方式 | 拍照，强项 | 手打，拍照是弱项 | 拍照为主，手打为辅 |
| 产物形态 | 分好类的文件 | 网状笔记 | 网状笔记，且由照片长出 |
| 结构由谁建 | 工具不建，用户自己建文件夹 | 用户手工建双链 | AI 提议，用户一键确认或拖动 |
| 增量处理 | 一次性整理 | 手工追加 | 每次新增都自动找位置，说不清就进未归类箱 |
| 检索依据 | 文件名 | 标题与手写双链 | 语义、符号、知识点三层 |
| 改错了怎么办 | 重新整理 | 手工改链接 | 拖一下，且这次修改会改变之后的行为 |

一句话区分：扫描工具把照片变成文件，笔记工具把文字变成网络，脉络把照片直接变成网络。

## 二、技术方案

### 2.1 总体架构

三段式：手机端负责拍、看、改；云端负责理解、对齐、索引；平板与网页端负责整理与复习。三端共享同一个数据模型，因此任何一端做的修改，另外两端立刻可见——这也是赛题鼓励的多设备接力。

| 层 | 组成 | 职责 |
| --- | --- | --- |
| 采集端（Android） | 相机与矫正、版面预览、节点卡片、拖拽改挂 | 拍得正、看得清、改得动；所有自动结果在这里可被否决 |
| 结构端（云端） | 版面分析、公式识别、结构对齐、关系推理、检索索引 | 把一张图变成节点，并决定它长在树上哪个位置 |
| 整理端（平板 / 网页） | 知识树视图、关系图、错题本、复习计划 | 大屏上的重排与复习；平板可手写批注 |

数据模型只有四张表，刻意保持简单：素材（原始图与版面）、节点（知识点与题目）、边（关系）、修订（谁在什么时候改了什么）。修订表是「可回溯」和「修正即反馈」两个特性的共同基础。

### 2.2 功能概述

| 模块 | 功能 | 首版范围 |
| --- | --- | --- |
| 拍摄与矫正 | 自动裁边、去阴影、透视校正、多页连续拍 | 全量 |
| 版面与识别 | 文字/公式/图形/表格分区，公式转 LaTeX，保留原图 | 文字与公式；图形只做区域保留 |
| 结构对齐 | 四选一关系判定 + 理由 + 置信度 + 未归类箱 | 单门课程，三层树（课程/章/知识点） |
| 知识树视图 | 树形浏览、拖拽改挂、批量归类、节点合并 | 全量 |
| 关系图 | 以知识点为中心的关系网络，展示跨章节连接 | 只读，可点击跳转 |
| 题目结构化 | 五槽位拆解，错题本按知识点重组 | 覆盖选择与计算两类 |
| 复习闭环 | 按遗忘曲线排复习顺序，薄弱点优先 | 基础版 |
| 多端同步 | 手机、平板、网页三端一致 | 手机 + 网页；平板复用网页 |

### 2.3 关键技术

#### 2.3.1 增量结构对齐

整条流水线分三步。每一步都为下一步留下可解释的中间结果，便于定位错误。

```
输入：新内容 x（一张图或一段识别结果）+ 当前知识树 T

① 候选生成（三路并行，各取前 10）
   语义路：x 的嵌入 与 所有节点标题+摘要 的嵌入 做近邻
   字面路：识别文本与节点标题、章节名做字符级匹配（中文短标题上这一路很有效）
   符号路：x 中的公式符号集合 与 各知识点高频符号集合 求交（理工科专用，命中率意外地高）

② 关系判定（一次结构化调用）
   输入：x 的摘要 + 候选节点及其父节点路径
   输出：{"relation": "挂载|扩展|新建|待定",
          "target": 节点 id 或空,
          "reason": "一句话理由",
          "confidence": 0.0–1.0}

③ 阈值分流（三个档位，行为不同）
   confidence ≥ 0.80  → 直接执行，并在卡片上标注「已归入 · 可改」
   0.55 ≤ conf < 0.80 → 执行，但标黄并出现在「待你确认」列表
   conf < 0.55        → 仅入未归类箱，不猜测
```

「符号路」是这套方案在理工科场景下的一个便宜而有效的偏方。学生问「这个公式在哪」，本质是在问符号；而符号集合的重合度对短文本标题极不敏感，恰好补上了语义路在短标题上的短板。

#### 2.3.2 未归类箱与批量确认

这是整套交互里最容易被低估的设计。逐条询问会让用户在第 3 次就想关掉应用；而静默丢弃会让结构永远起不来。折中做法是**延迟决策**：

- **积累。​**置信度低于阈值的条目进入未归类箱，界面上只有一个数字角标，不打断任何操作。
- **聚类。​**箱内条目达到 3–5 条时，先在箱内做一次小聚类，把同类的归成一堆。
- **一次问完。​**以一堆为单位提问：「这三条看着像新的一章『级数』，要开吗？」用户一次点击处理三条。
- **可延后。​**用户也可以选择「再等等」，箱子上限设为 30 条，超过则提升提示优先级。

#### 2.3.3 版面理解与公式管道

版面分区的目的不是好看，是为了让后续每一步只处理它该处理的部分：公式送公式识别、文字送文本识别、图形只保留区域。混在一起识别，是手写板书错误率高的主因。

| 步骤 | 做法 | 失败时的降级 |
| --- | --- | --- |
| 倾斜与裁边 | 角点检测 + 透视变换 | 保留原图，仅做亮度归一 |
| 分区 | 版面检测模型输出区域框与类别 | 退化为整页 OCR |
| 阅读顺序 | 按区域位置与栏数排序，处理双栏板书 | 按从上到下、从左到右 |
| 公式转写 | 公式区单独送识别，输出 LaTeX | 保留公式截图，允许用户手写修正 |
| 索引入库 | LaTeX 同时生成 MathML，建立符号索引 | 仅文本检索 |

#### 2.3.4 修正即反馈

用户每改一次分类，系统记一条修订：原建议、最终选择、内容特征、耗时。这些数据有两个用途：短期用于调整该课程的阈值，长期用于构造一个真实分布的对齐评测集。

```
修订记录 {
  content_id, course_id,
  suggested: {relation, target, confidence},
  chosen:    {relation, target},        // 与 suggested 不同即为一次修正
  time_to_decide_ms,                    // 犹豫时间也是信号
  created_at
}

每周批处理：
  统计各课程的修正率与混淆对（如「扩展 → 新建」被改得最多）
  对该课程的对齐提示词追加 3–5 条少样本示例
  重新校准阈值：把修正集中的置信度分布下移 0.05
```

#### 2.3.5 检索：三层召回

| 层 | 解决什么 | 实现 |
| --- | --- | --- |
| 语义层 | 「那个讲极限存在性的地方」 | 节点摘要与用户查询的向量近邻 |
| 符号层 | 「含 ε-δ 的那一页」 | MathML 符号索引，支持单符号与组合检索 |
| 结构层 | 「第三章下面所有跟连续有关的内容」 | 沿树与图遍历，支持按章节范围过滤 |

三层结果按统一分数融合后排序，展示时标明命中原因——让用户知道「为什么给你看这个」，是建立信任最便宜的方式。

#### 2.3.6 复习闭环

节点带一个掌握度，由三件事共同决定：被复习的次数与间隔、相关题目的正确率、以及用户手动标记的「还不熟」。复习顺序按「遗忘风险 × 薄弱程度 × 考纲权重」排序，而不是简单的时间轮转。

这里刻意不做「自动出题」和「一键总结」。理由和 1.5 一致：赛题要的是助教，不是代做。让 AI 替你总结完，你只是读了一遍；让你自己看着薄弱点去翻原来那页，才是复习。

#### 2.3.7 隐私与端云协同

- **原始图片默认留在本地。​**只有用户主动点「整理」时才上传，且上传后 24 小时清除。
- **云端只存结构化结果。​**节点、边、LaTeX 文本，不存原始照片。
- **可导出。​**全部笔记与结构可导出为 Markdown，兼容 Obsidian 的双链语法——我们不想做数据孤岛。
- **可离线。​**已同步的节点在本地可查可改，断网只影响新内容的整理。

最后一条值得多说一句：**支持导出成 Obsidian 格式**，看起来是在把用户送走，实际上是这个品类里最有效的信任建立方式。用户愿意把一学期的笔记交给你，前提是他随时能拿走。

### 2.4 工程质量保障

| 方面 | 做法 |
| --- | --- |
| 客户端 | Kotlin + Jetpack Compose，最低支持 Android 10；相机、矫正、本地 SQLite |
| 云端 | Python + FastAPI；版面与公式识别调用现成模型，不自研 |
| 模型 | 关系判定使用通用大模型接口，通过 JSON Schema 约束输出；所有结果带置信度 |
| 测试 | 对齐逻辑用固定知识树 + 固定输入做回归；识别链路录制真实照片做离线回放 |
| 可观测 | 每张图记录一条处理 trace：分区耗时、识别耗时、对齐置信度、是否被修正 |
| 规范 | 首周起启用分支策略、提交规范、静态检查与单元测试门禁；保留 AI 辅助编程的关键提示词 |

## 三、项目计划

### 3.1 可行性分析

技术可行性。方案中的每一段都建立在成熟能力之上：版面检测、公式识别、大模型结构化输出，都是可直接调用的现成接口。我们真正要写的，是**对齐逻辑、未归类箱、修订反馈​**这三块——它们都是纯软件逻辑，不依赖任何专有硬件或权限。这一点对本团队尤其重要：我们不具备做端侧模型训练的算力，也不需要。

资源可行性。一部普通 Android 手机即可完成主链路演示；平板环节用网页端在浏览器里模拟，决赛若取得设备再接入。识别类模型的调用按张计费，一学期三百张图的成本在数十元量级。

用户可行性。这是我们最占优的一点：**团队成员本人就是这个产品的目标用户**。手里有真实的课堂照片、真实的期末复习经历、真实的「找不到」的时刻。这意味着访谈不需要编造，测试不需要招募陌生人，两周试用就是把自己一学期的照片导进去。

已知局限。手写公式的识别准确率仍达不到免校对的程度，产品必须假设「一定会错」并围绕这一点设计；首版只支持理工科、只支持单门课程的三层树；跨课程的自动连接在首版只做展示不做自动合并。

## 附录 A　三分钟现场演示脚本

演示采用倒叙：**先让评委看到期末那个绝望的瞬间，再倒回去看它是怎么被避免的。​**这样做的原因是，整理类产品的价值在当下看不见，只在检索的那一刻兑现。

| 时间 | 画面 | 操作与旁白 |
| --- | --- | --- |
| 0:00–0:20 | 手机相册，滑过几百张模糊的板书照片 | 「这是一个学期。它们都在，但你找不到任何一张。」 |
| 0:20–0:50 | 现场拍一张新板书 | 矫正、分区、公式转写一气呵成。关键动作：把识别出的公式原图与 LaTeX 并排显示，指出一处被标黄的可疑符号 |
| 0:50–1:20 | 节点落位 | 系统提示「已归入 第三章 3.2 洛必达法则，置信 0.87」。点开理由：「公式含未定式与极限商结构」。评委可以当场让它改 |
| 1:20–1:45 | 制造不确定 | 再拍一张明显跨章节的内容。系统说「我不确定，先放进未归类箱」。打开箱子，五条攒在一起，一次问「要新开一章吗」 |
| 1:45–2:20 | 关系图与检索 | 切到关系图，展示「极限」与「级数」之间那条跨学期的连线。搜索「ε-δ」，三层召回同时命中板书、笔记与那道错题 |
| 2:20–2:40 | 错题反查 | 打开一道错题，系统标出「卡在 3.4 连续性的第二步」，并直接跳回三个月前那页手写推导 |
| 2:40–3:00 | 修正即反馈 | 打开修订面板：「你改过 37 次，最近两周的修正率从 41% 降到 12%。」 |

演示的三条兜底：所有识别与对齐结果准备离线缓存；准备完整预录视频应对现场网络异常；演示用照片均为团队自己拍摄，可公开。
